## 🏛️ Part 1: System Operational Architecture & Deployment

### Q1: Where does AISHA physically live?
AISHA does not exist as a heavy local application or software download. She is hosted entirely as a centralized, cloud-native Software-as-a-Service (SaaS) application across a decoupled compute-and-storage infrastructure:
* **The Application Layer (FastAPI Backend Engine):** Runs on a secure cloud-native virtual server instance (such as AWS, DigitalOcean, or Google Cloud). It hosts active asynchronous worker threads processing live network webhooks, text-cleaning routing scripts, and API connections.
* **The Storage & Memory Layer (PostgreSQL & Local File Storage):** Relational tables (users, shops, operating hours) and unstructured data slices (`wiki_chunks`) live in a dedicated PostgreSQL database instance on the same cloud drive. The original archival documents are stored in local SSD storage pools.
* **The Model Processing Layer (The LLM Endpoint):** The Large Language Model (LLM) logic is accessed through a secure, stateless API bridge. The server streams context data to the model on-the-fly and completely drops the memory footprint immediately after a message is generated, ensuring no private data is permanently cached in the LLM's workspace.

### Q2: Where do customers "get" the product and how do merchants set it up?
Because the entire engine is cloud-hosted, onboarding requires zero terminal compilation or local software installation. The setup executes via an online web-to-mobile registration loop:
1. **The Merchant Web Dashboard:** A retail merchant opens their computer browser and visits our platform's central website homepage (e.g., `://aishasales.com`). They sign up, create an account profile, and fulfill their platform subscription fee.
2. **The WhatsApp API Activation (The QR Link):** Upon successful payment, the merchant dashboard renders a temporary, encrypted WhatsApp Web QR Code generated by our underlying gateway handler. The store owner opens WhatsApp on their retail device, scans the QR code via *Linked Devices*, and instantly hooks their store's existing phone line to our cloud backend routing server.
3. **The End-User Interaction:** Retail shoppers do not visit our central website. They simply send standard WhatsApp text messages to the merchant's business telephone number. The incoming text webhook instantly triggers our cloud-based search and prompt assembly execution to stream a reply back to their chat screen within milliseconds.

## 🔄 Part 2: Tenant Lifecycles & The Registration Journey

### Q3: What happens behind the scenes the exact second a merchant registers an account?
The moment the registration button is clicked, our platform engine kicks off an atomic, multi-layered provisioning sequence to build a secure workspace:
* **Step 1: Relational Database Partitioning:** The engine writes a new profile record to the core user tables. The database generates a completely randomized, unique **`business_id` (UUIDv4)** that serves as that shop's unalterable security signature across the entire application network.
* **Step 2: File Directory Sandboxing:** The path routing system (`tenancy.py`) catches the new UUID token and immediately creates deep, isolated storage folders on the server's local SSD:
  * 📁 `knowledge_base/raw_uploads/<business_id>/` (For original document archives)
  * 📁 `knowledge_base/clean_wiki/<business_id>/` (For sanitized Markdown notes)
* **Step 3: Webhook Gateway Binding:** The system links the merchant's authenticated phone channel to this new UUID context. AISHA is now fully activated for that specific tenant, waiting silently for their first catalog document to be uploaded.

## 🛡️ Part 3: Bank-Grade Data Isolation & Leaking Prevention

### Q4: In a shared database setup, how is a merchant's private data prevented from leaking to rivals?
Data privacy boundaries are strictly enforced across three distinct layers of the application execution lifecycle to guarantee that data crossover leak errors are mathematically impossible:

  
* **Layer 1: Storage Tier Isolation (Path Sandboxing):** The file path resolver (`tenancy.py`) handles all file creation, reading, and deletion. It runs filename string filters that scrub out dangerous directory traversal symbols (`../` or `..\\`). This creates a rigid folder cage that blocks application pointers from breaking out of a business's allocated path boundaries.
* **Layer 2: Database Tier Isolation (Row-Level Security - RLS):** All paragraph rows inside our unified `wiki_chunks` storage table are tagged with a tracking `business_id` UUID column. Via our Alembic database migration script, we activate low-level PostgreSQL Row-Level Security:
  ```sql
  ALTER TABLE wiki_chunks ENABLE ROW LEVEL SECURITY;
  CREATE POLICY tenant_isolation_policy ON wiki_chunks 
  USING (business_id = current_setting('app.current_business_id'));
  ```
  Whenever a customer sends a message, our async database connection pool explicitly sets the active connection context to match the calling tenant's UUID string. PostgreSQL intercepts the lookup at its storage kernel layer. Even if an engineer updates our app code and introduces a critical loop bug, **the database itself physically hides all other merchants' rows**, completely preventing foreign data access.
* **Layer 3: Application Tier Isolation (Gated Prompt Generation):** When `manager.py` compiles the system prompt, it anchors the instructions inside an exclusive, closed text envelope. The system prompt strictly forces the model to act as a read-only companion: *"You must answer USING ONLY the context blocks provided below. If the answer cannot be found in the text, you must say 'I don't have that information'. Do not make things up."* Because foreign tenant data is never fetched by the RLS layer, it can never be injected into the prompt payload memory workspace.

## 🗺️ Part 4: Target Market, Commercial Positioning, & Global Number Hub

### Q5: Who is the target business for our product?
Our platform operates on a **B2B2C (Business-to-Business-to-Consumer)** Software-as-a-Service model:
* **The Paying Customer (The Tenant):** Retail shop merchants, independent e-commerce store operators, and commercial product brands (e.g., cosmetic boutiques, pharmacies, accessory shops) who want to automate their catalog querying, price quoting, order booking, and customer management workflows.
* **The Consumer:** Everyday mobile phone users browsing products on WhatsApp. They chat naturally with the automated shop assistant line to check size availabilities, review operational hours, ask for prices, or finalize item orders.

### Q6: What is the "Global Discovery Number" and where does it live?
The **Global Discovery Number** is a central, marketplace-facing telephone line owned directly by our SaaS platform. It acts as an **Automated Conversational Shopping Mall**.
* **Where it Lives:** The telephone line is registered on our central FastAPI application server using a specialized **Hub-and-Spoke Webhook Router** configuration inside `manager.py`. It shares the exact same infrastructure backend as the individual merchant accounts but runs a broad database lookup script.
* **How it Operates:** If a consumer has never heard of an individual shop but wants to browse the AISHA network, they can text this single Global Hub number: *"I am looking for premium leather shoes."*
  * **The Cross-Tenant Scan:** The global router intercepts the incoming word vectors, bypasses the standard single-tenant RLS constraint, and scans our global GIN search index to aggregate all business IDs that have the term "shoes" registered inside their catalog chunks.
  * **The Interactive Choice Menu:** The global bot texts the buyer a WhatsApp list menu showing matching retail stores (e.g., `[Shop 1: Sarah's Luxury Boutique]`, `[Shop 2: John's Shoes]`).
  * **The Session Redirection Lock:** The exact second the user clicks "Sarah's Luxury Boutique", our backend webhook intercepts the click event and updates our relational `Conversations` table, switching their session memory status to `FORWARDED` and setting their active pointer lock to Sarah's business UUID. 
  * From that moment on, any subsequent text the customer types into that same central chat line instantly triggers Sarah's specific RLS constraints and prompt generation blocks, mapping them directly to her business facts without the user ever switching to a different phone number.

## 💎 Part 5: Product Differentiators & Unique Competitive Edge

### Q7: Why would a business choose AISHA over millions of other bots or powerful global chat systems?
Most conversational systems across Africa and the global market are either **rigid menu pickers** or **unconstrained AI assistants**. Both architectures routinely fail commercial enterprises. AISHA is uniquely engineered to solve the three fatal flaws that cause traditional chatbots to fail:

#### 1. Flawless Fact Anchoring (Elimination of Pricing Liabilities)
Standard AI chat bots are generative, meaning they guess the next word based on probability. This leads to **hallucinations**, where a bot reads an unstructured file and confidently quotes an incorrect price (e.g., telling a customer a KSh 5,000 bag costs KSh 500). The merchant is legally compromised by a buyer demanding an item at a massive financial loss. 
* **The AISHA Edge:** Our application engine executes strict, hardware-accelerated **PostgreSQL GIN Full-Text Search indexing** to pull out *only* raw, verified Markdown data chunks right before a word is generated. If a price or parameter is missing from that specific text chunk, the AI is blocked from answering. This guarantees total pricing and inventory integrity.

#### 2. Localized Database-Tier Governance (PostgreSQL RLS)
Traditional platforms enforce data isolation at the application code tier using basic code loops (`if business_id == current_user.id:`). If a developer changes a file and makes a small syntax error, data can bleed, leaking sensitive wholesale supplier data or customer logs to a competitor's dashboard.
* **The AISHA Edge:** We offload isolation from mutable, human-written application file code down to the immutable, deep database architecture tier using **PostgreSQL Row-Level Security (RLS)**. The storage kernel itself physically filters out all foreign rows before returning data to the server memory, delivering bank-grade data security that is completely immune to application-level coding bugs.

#### 3. Low-Overhead, Sub-Millisecond Speed Performance (GIN vs. Vectors)
Powerful global bots rely on heavy **Vector Databases** (like Pinecone or Chroma) and embedding generation models. This requires taking every incoming customer text message, sending an expensive network API request to a third-party embedding calculation service, waiting for it to return a mathematical list of vector numbers, and then searching your database. This adds a sluggish 2-second delay to every text, frustrating WhatsApp buyers, while inflating API billing costs rapidly.
* **The AISHA Edge:** AISHA avoids vector databases entirely by running highly optimized, offline **GIN (Generalized Inverted Index) Full-Text Search** directly inside our relational PostgreSQL instance. Keyword queries complete locally in less than 5 milliseconds for zero shillings, allowing our platform to offer blazing-fast performance at an incredibly low operational server cost, making high-end automation affordable to merchants across emerging markets.
